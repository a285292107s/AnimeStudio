什么时候该用命令行

同一个下载里有两个 exe：AnimeStudio.GUI.exe 是界面，AnimeStudio.CLI.exe 是命令行。两者能力基本一样，批量本身两边都能做——界面里也能一次导出全部，只是每一批都得你亲手点一次，中途关了窗口就白跑。区别只在「下一步由谁决定」：界面你点，命令行由参数决定。值得换过去的有三种情况：

  • 一次要导几百上千个文件，而且还要反复来。界面每批点一次，命令行写成一行就行。
  • 要放进脚本或定时任务。没人盯着也能跑完。
  • 同一批包换着花样导。复制一行，改几个字。

这三种之外先用界面：看清列表、预览贴图、确认游戏选对，命令行都不给你。它也没有「列出内容」的选项，只想清点数量可以用 --map_op AssetMap --map_type None，扫一遍只数不写文件。

三条能直接复制的命令

三条都只用两个位置参数（输入在前、输出在后）加几个 flag。在解压出来的目录里打开终端，把路径换成你自己的就能跑。

AnimeStudio.CLI.exe "D:\Games\SR\StreamingAssets" "D:\Out\sr-textures" --game SR --types Texture2D Sprite

输入可以是文件或目录，给目录会连子目录一起扫；输出目录自动创建。--game SR 必填，决定用哪套解密规则。--types Texture2D Sprite 只要贴图和精灵。另外两个默认值刚好合用：--export_type Convert 转成 PNG 这类可读格式，--group_assets ByType 按类型分目录。

AnimeStudio.CLI.exe "D:\Games\ZZZ" "D:\Maps\zzz" --game ZZZ --map_op AssetMap --map_type MessagePack --map_name zzz-assets

这条不导资产，只建索引：扫完目录，在 D:\Maps\zzz\zzz-assets.map 里写下每个资产的名字、容器、来源包、PathID、类型、Hash 和偏移。默认写紧凑 v2 格式（同样的内容约小 5 倍），4 线程并行，并且把每个包的条目缓存下来——下次游戏更新只重扫变化的包，通常几秒完成。建图先写 .partial 再原子改名，中途失败不会破坏上一次的地图；想再快一点可以加 --no_hash 跳过 Hash 计算。想知道时间花在哪，设 ANIMESTUDIO_MAP_PROFILE=1 再跑，结束日志会多一行 load / parse / hash / serialize 的分段耗时。

AnimeStudio.CLI.exe "D:\Games\ZZZ" "D:\Out\zzz-ui" --game ZZZ --map_op AssetMap,Load --map_type MessagePack --map_name "D:\Maps\zzz\zzz-assets.map" --names "ui_.*" --types Sprite

这条读上一条的索引，只加载名字匹配 ui_.* 的精灵所在的包，再导出。AssetMap,Load 就是「用现成的 map」，所以 --map_name 要给带 .map 的完整路径。

过滤器可以写在文件里

--names 和 --containers 允许只给一个文件名：程序逐行读它，每行当一条正则。手写一份清单存成 txt 传进去，比在命令行里堆一长串正则干净。空行跳过，写错的正则静默忽略。

三个必须知道的坑

  1. --types 用空格，不用逗号

    仓库 README 里那条示例写的是 --types Texture2D,Sprite，这是错的。逗号让整串变成一个词，程序拿它去匹配类型名，失败后只打一行 has invalid format, skipping... 就跳过——不报错、不退出。

    等所有类型都被跳过，过滤器就空了，结果是把整个包全导出来：你想只要贴图，得到的是一整个目录。

  2. --game 不给就是报错

    它必填，还挂着校验器比对候选名单：不给，拿到的是错误信息加用法说明；给错，是 Invalid game. Supported games: ... 加一长串名单。README 说「不带参数运行会列出完整参数」，实际你看到的是缺必填项的报错。

    名单里是枚举名（GI、SR、ZZZ），不是界面下拉里的「Live」「CBT 2」——那是另一个字段。界面选「Live」，命令行要写 --game SR。

  3. 退出码永远是 0

    程序入口把命令行组件的返回值丢掉，执行函数没有返回值，还把异常全吞进 catch 里打印。所以失败时进程照样以 0 退出：%ERRORLEVEL%、$LASTEXITCODE、CI 的红灯都指望不上。

    判成败只能看产物：目录里有没有新文件、日志里有没有 Error、文件数量和预期对不对得上。

一个文件一个文件地干

扫完目录，它先按路径字符串长度从小到大排一遍——不是按文件大小——再逐个文件走三步：加载、建资产表、导出，然后清空处理下一个。

所以内存峰值只跟「最大的那一个文件」有关。界面版反过来：一次把所有文件读进内存、建一棵全局树再导出，内存跟整个目录成正比。经验上差一个数量级——几百 MB 的目录，界面版峰值按 GB 算，命令行通常几十到几百 MB。界面一打开就吃满内存的目录，命令行往往能跑完。

代价是没有进度条，也没法先看结果再决定。

资产地图：先建索引再回捞

比喻是图书馆的索引卡：不建索引，每次找书都要翻整个书库；建了索引，卡片告诉你去哪个书架哪一排。

每次导出都要解包、读对象头、算资产名，整包扫一遍几分钟到几十分钟。建 map 就是把这趟活儿一次做完，之后只读卡片。值得建的三种情况：

  • 整包扫描。先把整个安装目录索引成一张表，再决定要哪一些。
  • 反复导出。今天要贴图、明天要动作，建一次能用很多次。
  • 版本对比。两份 map 一比，就知道这次更新加了什么、删了什么。

.map（MessagePack）每条存七样：名字、容器、来源包、PathID、类型、Hash、偏移。.xml 只存前五样，没有 Hash 也没有偏移——要比版本差异、要用偏移回捞，就得用 .map 或 .json。

CAB map 是另一份东西，落在工作目录的 Maps\<名字>.bin，不是输出目录。它按 CAB 名记两件事：这个 CAB 在哪个包的哪个字节偏移、依赖哪些别的 CAB。有了偏移，加载时只从需要的位置解开，不必整包读完，所以超大包先建 CAB map 再导提升明显。

顺带一个反直觉的地方：Load 位在这两个分支里含义相反——AssetMap,Load 是读图，CABMap,Load 是建图；单独写 --map_op CABMap 才是去读 Maps\ 下的旧图。

Asset Browser 能干什么

Asset Browser 是专门读 map 的工具（菜单的 Load AssetMap），只认 .map 和 .json，不认 .xml。

新版 Host/CLI 默认写紧凑 v2 地图（--map_format Compact，同样 733 万条时从 1.93 GB 降到约 386 MB），并按文件做增量缓存：游戏补丁后重建只重扫变化的包，通常几秒。老的 Asset Browser 不认 v2，要给它看就加 --map_format MessagePack 重建成旧格式；网页宿主和 CLI 的 AssetMap,Load 两种格式都能读，--threads 控制建图并行度（默认 4）。

它能做的五件事：

  • 按属性过滤。名字、容器、来源、PathID、类型、Hash 各一格，填的是正则，回车就筛。
  • 按类型多选。Select Types，一次勾好几种类型。
  • 直接回捞。Load Selected 只加载选中的，Export Selected 只导出选中的。
  • relocate。把 map 里记的源路径整体平移到另一次安装目录。
  • 两张 map 对比。Load second map 之后，在三种视角里选一种。
对比的三个视角，对应下拉里的三项
下拉项你看到的是实际含义
Assets Only in First Map第一张有、第二张没有新版删掉的
Assets Only in Second Map第二张有、第一张没有新版新增的
Assets with Differences两边都有但 Hash 不同内容改过的

relocate 只比文件名、不比子目录，不同目录里的同名包会串；跑完会告诉你多少个没搬过去。

对比版本的真实局限

超过 16 MB 的对象没有真 Hash

建图时，大于等于 16 MiB 的条目会把 Hash 写成 size:1a2b3c 这样的字符串（十六进制字节数），而不是内容哈希——上百 MB 的着色器和网格只为索引身份算一遍不划算。后果很实在：同一个大对象在两版之间只要大小没变，就永远显示「没改过」，只能靠大小、偏移或手动核对。

另一个边界是「同一个资产」怎么认：用名字、容器、PathID 三元组。重新导入让 PathID 变了，就会被算成「删一条加一条」，而不是「改过」。

界面和命令行不一样

同一个包，两边产物不是逐文件对得上的

已知的十几处差异里有这三条：同名文件去重，界面从 (1) 开始编号，命令行从 (0) 开始；ByContainer 遇到空容器，界面回退到输出根目录，命令行回退到类型子目录；动作导出的 FBX，命令行那条路径不拼 .fbx 后缀，产物没有扩展名。

要做长期流水线就固定用一边，别混着比。
