仓库是怎么分层的

托管代码的依赖只有一层：从上往下，没有回环。把每个项目的项目引用列出来就是全貌：

AnimeStudio.GUI        → Utility, AnimeStudio
AnimeStudio.CLI        → Utility, AnimeStudio
AnimeStudio.Utility    → FBXWrapper, PInvoke, AnimeStudio
AnimeStudio.FBXWrapper → PInvoke, AnimeStudio
AnimeStudio.PInvoke    → （无）
AnimeStudio            → （无）
AnimeStudio.Patcher    → （无）

核心项目 AnimeStudio 不引用任何项目，是最底下的叶子，包解析、序列化文件、对象模型、贴图解码和资产地图全在里面。AnimeStudio.Patcher 完全独立，只跟 exe 文件的字节打交道。8 个 C++ 项目不被任何托管项目引用，它们只往 AnimeStudio.Libraries 里吐 DLL，再由三个 csproj 登记进发布包。

15 个项目一张表

7 个托管项目加 8 个原生项目。「产出」只写类型，文件名与项目名相同，比如 AnimeStudio.Utility.dll。「随构建」问的是「是否随 solution 构建」。

最后那一列容易看错

.slnx 里只有 AnimeStudio.Ooz 和 AnimeStudio.FBXNative 标了 <Build Project="false" />，solution 构建不碰它们；5 个 ACL 和 HLSLDecompiler 会跟着编。README 说「原生库都排除在 solution 构建之外」，跟 .slnx 的实际标注不一致。

构建

  • 前置。Visual Studio 2026，勾上「.NET 桌面开发」和「使用 C++ 的桌面开发」；只需要 .NET 10 SDK（不再兼容 .NET 9）。
  • build.ps1 干的活。编托管代码（CLI / GUI / WebView2 Host，单目标 net10.0-windows），用 Patcher 改写 GUI 与 CLI 的 apphost，最后归到 dist/：根目录是 AnimeStudio.GUI.exe 与 AnimeStudio.CLI.exe；dist/bin/AnimeStudio.Host.exe 是新的网页界面宿主，前端在 bin/wwwroot，它会自动在上层目录找 CLI。
  • 它不干的活。不编任何原生项目，不跑测试（仓库里没有测试项目），不签名不压缩。
  • 原生 DLL。9 个，共 7.65 MB，直接提交在 AnimeStudio.Libraries 里。它们的登记分散在三个 csproj：核心项目带 Ooz 和 FBXNative，Utility 带 HLSL 和 5 个 ACL，界面工程单独带 FMOD。
  • FBX 原生库。要 Autodesk FBX SDK 的 2020.3.7 版，头文件目录、一个 Debug 一个 Release 的库目录，全部以绝对路径写死在 AnimeStudio.FBXNative.vcxproj 的 4 处。装到别的位置就编不过。

日常开发不需要打包

改托管代码时 dotnet build AnimeStudio.GUI 就够了，产物里原生 DLL 会自动被拷过去。打包那一步只在要出安装包时才需要。

为什么要全都塞进 bin

发布产物长这样：根目录只有两个 exe 加一份 LICENSE，其余托管 dll、依赖清单和原生 DLL 全在 bin/。

dist/net10.0-windows/
├─ AnimeStudio.GUI.exe
├─ AnimeStudio.CLI.exe
├─ LICENSE
└─ bin/      托管 dll、deps.json、runtimeconfig.json、9 个原生 DLL

原因是 .NET 的 exe 只是个启动器：它把自己二进制里硬编码了「入口 dll 叫什么名字」，默认去同目录找同名 dll。想让 exe 待在根、dll 待在 bin/，就得把内嵌的这串路径改成 bin\X.dll。AnimeStudio.Patcher 就干这一件事：找到那串字节的起点，把 1024 字节的槽位清零，写进新路径。

好处很实在：两个 exe 共享同一个 bin/，公共依赖只存一份，体积几乎减半；用户桌面只有两个图标加一个文件夹。

代价是耦合：DllLoader 必须先看 exe 目录下有没有 bin/，有就切进去再找原生 DLL。想改发布布局，build.ps1 和 DllLoader 得一起改，只改一边就是运行期「找不到 DLL」。

加一个游戏要动哪四处

  1. 枚举里加成员

    在 GameType 里加一个名字。这个名字就是命令行 --game 的取值，也是内部到处比较的那个标识。

  2. 谓词里加分支

    同一文件下方那串 IsXxx(this GameType)，是核心库判断「这套规则跟谁像」用的。再加进 IsBlockFile、各个 IsXxxGroup 这类组合，解析分支才认得它。

  3. LoadGames 里注册

    一行 Games.Add(...)，把枚举、显示名、分类挂上去。显示名是界面下拉框里看到的那串字，跟命令行用的枚举名是两个字段。

  4. 需要密钥就换 record

    只改了文件头就用 Game；要扩展密钥、初始化向量就用 Blk；魔改 AES 用 Mr0k；UnityCN 系用 UnityCNGame，名字和密钥从 CNKeys.json 读。

这四处只让程序「认得」这个游戏。如果它的资源布局跟已有的都不同，还得回到下一节的容器与加密去加分支。

加格式、加容器、加加密

加一种导出格式，比如 glTF

  • ExportType 枚举加成员：AnimeStudio/ExportType.cs。
  • 分发 switch 改两份：AnimeStudio.GUI/Exporter.cs 和 AnimeStudio.CLI/Exporter.cs，这两份是同构的。
  • 外层调度的 switch 也两份：两个 Studio.cs。
  • 界面菜单：每个新格式要加三个菜单项和三个中转方法，否则界面上根本点不到。

加一种容器

  • FileType 枚举加成员：AnimeStudio/FileType.cs。
  • 魔数识别加一支：FileReader.CheckFileType，一条按签名长度分组的 if 链。
  • 加载分派加 case：AssetsManager.LoadFile，块文件还要加在 LoadGameBlockFile。

加一种块加密

  • 写解密函数：放 ImportHelper 或 Crypto/ 下的工具类里，一个静态方法进、一个 FileReader 出。
  • 预处理链加一支：FileReaderExtensions.PreProcessing 里按 GameType 分派的 switch，一个游戏一个 case。
  • 加密只包住块数据时还要去 BundleFile：解块的位置已经堆了 Mr0k、UnityCN、NetEase、FairGuard 一串分支。

结构性问题

准备 fork 的话，这几件事早晚会撞上。

按「撞上的概率」排，不是按严重程度
问题具体表现影响
全局可变静态状态游戏、导出表、类型开关、进度、日志全是静态字段不能同时开两个会话；写单元测试得先把全局摆好
两份业务代码界面版与命令行版的 Exporter.cs 有 86% 非空行逐字相同，Studio.cs 是 63%改导出逻辑要改两遍，已经漂了十几处
5 份 ACL 源码树5 个 ACL 工程各自带一份 acl/ 源码树，其中 4 个还带 rtm/上游更新要手工同步五次
apphost 的假设Patcher 假设内嵌路径槽位够 1024 字节、以零结尾，原串是裸 dll 名.NET 换掉 apphost 布局，构建期就抛错，比运行期崩好
许可证混合仓库是 MIT，但 kraken.cpp 带 GPLv3 头，FMOD 是免费非商用，FBX SDK 受 Autodesk 条款约束商业闭源分发之前必须逐项处理

一句话结论

适合贡献，不适合直接做生意

这个项目适合给它提 PR——加游戏、修解析、补导出的 PR 都欢迎，改法就是上面那几处锚点。但它不适合拿去做商业闭源分发：许可证是混的，两份前端代码会持续漂移，发布形态也建立在对 .NET apphost 的字节级假设上。
