它怎么工作

从你双击一个 .bundle，到桌面出现一张 PNG，中间有七层。这一页把它们一层一层拆开，每一层都回答三个问题：它在做什么、它凭什么能做、它做砸了你会看到什么。

一、认：先弄清你手里是什么

工具做的第一件事不是解密，而是看开头。它读文件最前面二十个字节，把里面的字符串读出来，比对几个固定的签名：UnityFS、UnityWeb、UnityRaw、UnityArchive、UnityWebData1.0、blk、ENCR。

对不上也不放弃。它接着按字节特征一路试下去：VFS 容器、gzip、brotli、未压缩的 .assets、zip、mhy 系列、Blb、HYG、Naraka、gunfire，最后兜底当成「裸资源文件」。这一步的结论只有一件事：这个文件属于十五种类型里的哪一种。

为什么这一步重要

后面的每一层都按类型分叉。类型认错，后面全部白做——而且不会报错，只会给你一堆看起来像数据的东西。

二、开锁：整文件这一层

有些游戏不改包里面的结构，而是在外面又套了一层：换个假头、整体异或、按固定规则重排字节。这一层要处理的就是这些，它必须把整个文件读进内存，换出一个新的「阅读器」交给下一层。

这里有二十多个分支，一个游戏一个。偶像梦幻祭、闪耀暖暖、重返未来 1999、少女前线、世界计划、恋与深空、动物派对……各自一套写法。名字都在游戏与它们的锁里。

同一层还干一件容易被忽略的事：判断这是不是一个「包里套包」的容器。它会读包头的长度字段，和文件的真实长度比一下。对不上，就说明这个文件里塞了不止一个包，于是标记成块文件，等下一层逐个拆。

你会看到的证据

星穹铁道的 .block 就是这个样子：一个文件里躺着几十上百个 ENCR 包，每个都得单独拆开。

三、拆箱：容器这一层

到这里才真正开始拆包。一个 UnityFS 文件由三部分组成：头（版本与标志位）、块表（数据被切成几块、每块压缩后多大、解压后多大）、目录（里面每个文件的名字与偏移）。

块表本身也可能是压缩的，所以顺序是：先解块表，再按块表解数据。压缩方式就那么几种：

容器里能遇到的压缩方式，以及谁来解它
压缩方式谁来解在哪见到
不压缩直接读少数小包
LZMA内置的 7-Zip 解码器老一点的包
LZ4 / LZ4HC内置的 LZ4 解码器绝大多数 UnityFS
Oodle（Kraken 等）原生库 AnimeStudio.Ooz.dll星穹铁道、绝区零
非标准 LZ4 变体专门的变体解码器来自星尘、明日方舟

厂商的第二次手脚也发生在这一层：容器的头本身可能被改过（UnityCN 的密钥区块、mt19937 生成的异或垫），数据块也可能在压缩之前就先被处理过一次。所以「解压」和「解密」在这里是交替的，不是两步分开走。

拆完之后，包里的每个文件都被标好了偏移与长度。它不会真的把几十兆数据复制一份——小包直接在内存里开窗口，大包落到临时文件，切出来的每一段都是同一块内存的视图。

四、读清单：SerializedFile

包里的 .assets 文件是真正装着好东西的地方。它的结构很像一本书：

头
元数据多大、文件多大、格式版本、数据从第几个字节开始、字节序。
类型表
这个文件里出现过哪些类型，每个类型的编号是什么。
对象表
每个对象一条记录：类型、包内编号（pathID）、从第几个字节开始、多长。
脚本表与外部引用
MonoBehaviour 挂在哪个脚本上；这个文件还依赖哪些别的文件。

还有一份叫 TypeTree 的东西：某些版本会把「每个类型有哪些字段、字段什么顺序」也写进文件。有它，工具就能把 MonoBehaviour 里那些看不懂的二进制还原成带键名的 JSON；没有它，就只能靠内置的类型定义去猜。

五、造对象

清单读完了，接着按类型逐个造对象：贴图、精灵、网格、材质、音频、动画、字体、着色器、文本……三十多种。每一种都知道自己该怎么从那一段字节里读出字段。

这一步是整个流程里最慢的地方，原因很朴素：同一个文件的读取位置只有一份。每个对象都要先把读取位置挪到自己的起点，读完再挪回去。所以它没法并行，只能一个一个来。这就是为什么导出一个几万资产的游戏要等很久。

单个对象读失败不会中断整批：记一条日志，跳到下一个。

六、串关系

对象造出来的时候彼此不认识。这一步把它们接起来：

  • 每个 GameObject 的组件槽位，回填成真正的对象引用。
  • 精灵图集把散落的精灵收回自己名下。
  • 绝区零这种把网格拆开存的游戏，还要按名字重新挂回去——这一步是启发式的，也是它导模型偶尔会缺件的原因。

七、写文件

最后一步最直白，但选择最多。你要决定两件事：导什么，和导成什么。

导什么：全部 / 选中 / 过滤后
整包导出、只导你在列表里勾中的、或者只导当前过滤器命中的。
导成什么：转换 / 原始 / 字段 / JSON
转换是转成人能打开的文件（PNG、OBJ、WAV、.txt）；原始是把字节原样吐成 .dat；字段是把对象内容打成文本；JSON 是整个对象序列化。
放哪儿：按类型 / 按容器 / 按来源 / 平铺
四种目录排法。按容器最贴近游戏原本的组织方式，按来源最稳定但目录最深。

重名的时候默认只写第一份，后面同名的跳过且不提示。想全都留下，得去开「允许重复」。

为什么它慢，为什么它吃内存

三个原因叠在一起：

  1. 对象只能一个一个读

    共享一个读取位置，天然不能并行。这是设计约束，不是没优化。

  2. 一个包解压后可能非常大

    解压结果超过 512 MB 就不再放内存，改用临时文件；整块内存还被所有切出来的片段共用，所以只要有一个片段活着，整块就回收不掉。

  3. 它会在后台主动回收内存

    每处理完一个包强制回收一次，每三十来个文件再来一次。这是被大包撑爆过之后留下的补丁。

它会怎么失败

这个工具的默认姿态是「尽量别崩」：容器打不开就跳过这个文件，对象读不出来就跳过这个对象，最后你看到的是「少了一些东西」而不是一条明确的错误。

三种真的会停下来的情况

版本信息缺失且无法推断时、块尺寸不合理时、块表越界时。除了这三种，其它问题大多会安静地降级——这也解释了为什么排错的第一条永远是「先确认游戏选对了」。
