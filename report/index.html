七个跳点，每一跳都有名字

点任意一跳，看它读什么、写什么、把什么交给了下一跳。每一条都给了可以直接跳转的 file:line。

先用 20 个字节认脸，认不出再逐字节试

构造 FileReader 时就完成嗅探：先读 20 字节的签名字符串匹配 UnityFS、UnityWeb、UnityRaw、UnityArchive、UnityWebData1.0、blk、ENCR，不中就走字节签名级联，从 VFS、gzip、brotli 一路试到 mhy0、Blb、HYG、Naraka，最后兜底成 ResourceFile。

输入
磁盘上的一个路径
输出
FileType，共 15 种容器类型
判据
字符串签名 + 六组字节特征 + m_FileSize == stream.Length
坑：FileReader.cs:37 的级联顺序是有意义的。把 gzip 的检查放到 SerializedFile 前面，所有未压缩的 .assets 都会被当成 gzip 喂给解压器。

锚点：AnimeStudio/FileReader.cs:37 · CheckFileType

整文件解密和容器识别，挤在同一个函数里

PreProcessing 做两件事。一是 switch (game.Type) 分发 21 个厂商整文件解密器；二是读出头里的 size 字段，一旦发现它不等于文件实际长度，就把这个文件降级成 BlockFile。星穹铁道的 .block 里塞着上百个 ENCR，就是在这里被认出来的。

输入
一个已嗅探的 FileReader
输出
另一个 FileReader，新 stream，旧的要自己 Dispose
规模
17 个 Decrypt + 2 个 Parse + 2 个 Decompress
坑：这一层必须整文件读进内存。想让大包流式处理，改这里没有用，得把 L1 拆成按块的范围解密。

锚点：AnimeStudio/FileReader.cs:183 · PreProcessing

七路容器，靠两个成员名接头

LoadGameBlockFile 一个 switch 覆盖 UnityFS、ENCR、blk、mhy、Blb、HYG、VFS、lpak 八种形态。所有容器对象最后都被 dynamic 消费，只要求暴露两个成员：m_Header 和 fileList。成员名拼错，编译期不会报错，运行时才炸。

输入

输出
List<StreamFile>，AssetBundle 里每个节点一份
关键

坑：这是全库唯一的容器契约，也是唯一的隐式契约。想加新容器，照抄 m_Header 加 fileList 的形状，别自作聪明抽接口。

锚点：AnimeStudio/AssetsManager.cs:660 · AnimeStudio/BundleFile.cs:124

六个厂商的判断，是一条顺序 if 链

ReadBlocks 里逐块解压，先过 NetEase 的 LZMA 首块，再过 Oodle 家族，再在 LZ4 家族里塞 WMV 的首块异或，然后依次尝试 mr0k、UnityCN、NetEase、FairGuard、OPFP。UnityCN 的判定就是块头里那个 0x100 位。

输入
StorageBlock[]，每块带压缩类型与 flag
输出
解压后的共享缓冲，或一个 path.temp 临时文件
阈值
总解压量不超过 512MB 走内存，否则落盘
坑：这六个判断是顺序 if 而不是 else if。当前游戏矩阵下它们互斥，但新增一个厂商时，一个包同时命中两条就是叠加解密，症状是「解出来还是乱码，但前 16 字节正确」。

锚点：AnimeStudio/BundleFile.cs:590 · ReadBlocks

UnityCN 密钥链路是这套设计里最干净的一段

内置 24 条默认密钥，持久化在 exe 旁的 CNKeys.json，首次运行若读不到就重写成默认表。选中的 key 经 UnityCN.SetKey 下发到一个静态的 ICryptoTransform。头部里有一段自校验：用 key 解出来的签名必须等于两串公开魔数之一，这是判断「key 选对没有」的唯一探针。

静态单 key 带来一个硬约束：同一进程不能同时解两个不同的 UnityCN 游戏。想做多开或批处理，这是第一处必须改成实例作用域的地方。好消息是接入一款新的 UnityCN 游戏不需要改代码，往 CNKeys.json 加一行、枚举加一个成员就够。

拖动滑块，看一个 AssetBundle 会被放进内存还是落到磁盘上。阈值和分支都来自真实代码，不是估算。

错误模型是「静默降级」，这是最容易误判的地方

容器级失败只记日志然后返回，调用方看到的是 assetsFileList 少了几项，不是异常。对象级失败逐条 catch，把名称、路径、类型、pathID 打进日志后继续。真正的硬失败只有三处：版本缺失、块尺寸非法、blocksInfo 越界。

对于批处理场景，这意味着退出码为 0 不代表全部解析成功。做二次开发时要先把日志里的失败计数提炼成结构化结果，否则自动化流水线会静默丢资产。

许可不是统一的，商用前必须核对

仓库根目录是 MIT，但 AnimeStudio.Ooz/kraken.cpp 的文件头是 GPLv3，而它是 Oodle 解压的唯一入口。另外 AnimeStudio.FMOD.dll 是 2016 年的免费非商用版。内部工具无所谓，准备对外分发或商用，这两处必须先处理。

可复现性有三处硬伤

FBX SDK 2020.3.7 的绝对路径硬编码在四个地方，没有环境变量回退，也没有 vcpkg，换台机器第一天就卡住。预编译二进制没有溯源，资源文件版本号恒为 1.0.0.x，源码与二进制可能已经漂移。单独用 msbuild 编 vcxproj 时 $(SolutionDir) 为空，DLL 会落到盘符根目录。

那个 bin 目录是三方妥协的产物

发行包根目录只放两个 exe，所有托管 dll 进 bin/。原因有三：只露两个文件给用户、CLI 与 GUI 共享同一个 bin、以及 DLL 加载器会反向探测 bin 目录。代价是要一个构建期的 Patcher 去改写 apphost 里内嵌的入口路径，还要三层防护处理历史上出现过的 bin\bin\ 堆叠。

不值得照抄结构，值得照抄覆盖面：52 款游戏、22 个格式版本、10 类密码族跑在同一条管线上。

它的强项是「把不可能变成能跑」，弱项是「把能跑变成能维护」。所有复杂度都集中在四个文件、一个 dynamic 契约和一串顺序 if 上，这既是接一款新游戏只需改十几行的原因，也是它没法直接长成产品的原由。

二次开发的真正分水岭不在功能，而在要不要并发、要不要 headless。这两个问题一旦答「要」，第三步和第四步就必须做完；如果只是给现有 GUI 加几个导出格式，那合并两份 Exporter 就已经够用。
